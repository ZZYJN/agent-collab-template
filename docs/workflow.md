# 研发流程规范（workflow）— 受控子规范

> 消费者：所有代理（接到新需求 / 变更 / 开工前必读）与人类。与 AGENTS.md 冲突时以 AGENTS.md 为准；修改本文件须经用户批准。

## 0. 一图流

```
需求 / 变更（飞书或口头）
  │ ① 判级（编排者提出；trivial 之外均报人确认）
  ├─ trivial      → 快速通道：直接改 + 自跑验证 + commit（正文写明原因与验证方式）。到此结束。
  ├─ normal-lite  → 免文档修订：建完整任务书（引用其符合的已批 RFC）→ 进 ④
  ├─ normal       → ② 文档先行：动需求改 PRD（主研发 + PM 批）；动设计改 RFC（主研发批）
  └─ major       → 同 normal，另加：长期难逆取舍写 ADR + 提交前人工复核代码
  ③ 文档 approved（人签，见 §2）
  ④ 拆解：编排者建任务书（范围 / 禁区 / 验收 / 验证 / 追溯字段），status: ready，
     **先提交任务书**（契约冻结进 HEAD），再记录 base_sha
  ⑤ 派工：codex exec → 实现者写代码 + 测试 → 回写实现报告（status: implemented）
  ⑥ 评审：编排者按 §5 审查并独立复跑 → 通过 status: reviewed；不通过回 ⑤（≤2 轮，第 3 次升级给人）
  ⑦ 实现提交：编排者 commit（[codex] + T-NNN + trailers，含代码与任务书）
  ⑧ 收尾提交：[claude] T-NNN 收尾——回填 commit SHA、status: done → 需要时同步摘要给 PM
```

新需求与需求变更走同一条流程，区别只在判级。

## 1. 变更分级（按风险判，不按行数判）

- **trivial**：须同时满足——不触碰生产配置、权限、安全敏感面、数据结构/存储、依赖、对外接口；**不改变行为语义**；影响局部且可逆。例：注释与文档错别字、纯文案修正。行数（约 ≤20）只是参考信号，不是判据。**行为语义的修正（含 bug 修复）不属于 trivial。**
  → 快速通道：**只能由编排者或人执行**（实现者无提交权），写者可兼查者，可先斩后奏；commit 前必须自跑相关验证，commit 正文写明原因与验证方式。不建任务书、不记 DEVLOG。
- **normal-lite**：行为有变，但完全符合某份已 approved RFC 的既有设计、不改用户可感知契约、无新依赖与数据结构变化。例：按既有设计补一个接口实现、修一个有明确复现的局部 bug。
  → 免 PRD/RFC 修订，直接建**完整任务书**（引用所符合的 RFC 章节），其余环节（派工、异角色评审、提交）照走。
- **normal**：新功能，或用户可感知的契约 / 行为设计变化。→ 全流程；PRD 动不动由"需求本身是否变化"判定。
- **major**：架构调整、数据迁移、或触及 AGENTS.md 敏感动作签核表中的领域。→ 全流程 + ADR（若属长期难逆取舍）+ 提交前人工复核代码。

判级由编排者提出：trivial 可先斩后奏，其余须人确认后再动文档或代码。**拿不准就按高一级处理。**

## 2. 状态机（两套，不混用）

**文档（PRD / RFC）**：`draft → in-review → approved → superseded`

- approved **只能由人签出**：frontmatter 填 `approvers`（PRD 两人、RFC 一人）与 `approved_version`；以承载该版本的 git 提交为批准基线。
- **批准基线不可变**：已 approved 的正文不得修改。语义变化 → `version + 1`、状态退回 in-review、重批；旧版本标 superseded。实现期补充只能写进 RFC「附录：实现决策回写」（非规范性，不得与正文冲突）。
- 实现中发现文档与现实冲突：停止实现，按上一条升版重批后再继续。
- 升版期间无须为每个版本建独立文件：工作区文件即候选版（in-review），**最近批准版 = git 历史中 `approved_version` 对应提交的内容**，在新版批准前持续有效。
- ADR 同理：由人批准（「批准人」字段）方为已采纳；已采纳不改正文，用新 ADR 取代。

**任务书**：`intake → ready → implemented → reviewed → done`（辅助态 `blocked` / `cancelled`）

- `ready` 由编排者置，前提：上游文档 approved，或 normal-lite 判定成立且经人确认；
- `implemented` 由实现者置；`reviewed` 由评审者置；`done` 在提交完成、追溯字段补齐后由编排者置；
- 任务书全生命周期**不使用 approved 一词**；
- 编号取 `docs/tasks/` 现存最大号 +1（单一写者纪律保证无竞态）。

## 3. 任务书协议（派工契约 + 追溯记录）

一个任务一个文件 `docs/tasks/T-NNN-<slug>.md`（模板见 `templates/task-template.md`）。normal-lite 及以上必须形成完整追溯链：

**PRD@version → RFC@version → 任务书 → base_sha → 评审记录 → commit SHA → 测试证据（验证结果）**
（需求未变时，PRD 经 RFC frontmatter 的 `prd` 字段间接追溯，任务书 `prd` 字段可空）

正文必含：背景与上游文档（指向具体章节）、范围、禁区、验收场景（Given/When/Then）、验证方式、实现报告（实现者回写）、评审记录（评审者回写）。
frontmatter 追溯字段：`base_sha`（派工时 HEAD）、`commit`（完成提交）、`agent`（实现者 model / CLI 版本）、`session`（派工会话 id）。

## 4. 派工机制（编排者 → 实现者）

本机已验证 codex-cli 0.145.0（CLI 升级后先 `codex exec --help` 复核）。本节命令是当前扮演者的事实性实现，换实现者时整节替换，流程不变（ADR-002）：

```bash
codex exec \
  -C "$(git rev-parse --show-toplevel)" \
  -s workspace-write \
  -o <scratchpad>/T-NNN-last.md \
  "你是本项目的实现者（角色见 AGENTS.md）。读取 docs/tasks/T-NNN-<slug>.md，严格按任务书执行；
   完成后把实现报告回写进任务书，并把任务书 status 改为 implemented。
   不要执行 git commit，不要改范围外文件，不要改动任何文档的批准状态。"
```

- **契约冻结**：派工前任务书必须已提交（契约在 HEAD 中）——实现者若改动范围 / 禁区 / 验收，会在 `git diff HEAD` 中直接现形；实现者只允许改动「实现报告」节和 status → implemented。
- 派工期间编排者**不得并行修改仓库**（单一写者，见 AGENTS.md「并发与写入纪律」）。
- 派工前把当前 HEAD 记入任务书 `base_sha`；派工输出中的 session id 记入 `session`；实现者 model / CLI 版本记入 `agent`。
- 返工 / 追问用 `codex exec resume <session-id>`（显式 id）；取不到 id 就重新派工并在任务书标注，**禁止 `resume --last`**。
- 沙箱默认禁网：装依赖由编排者在派工前处理，或经人批准临时放开。
- 派工失败 / 超时 / 输出异常：**脱敏后**记入评审记录（密钥 / token / 个人信息打码）→ 拆小重派一次 → 仍失败升级给人。

## 5. 评审协议（评审者）

**评审输入（缺一不可）**：
1. `git status --short --untracked-files=all` 全量清单（必须带 `--untracked-files=all`，否则新目录被折叠成一行、内部文件不可见）——确认改动文件集合与任务书范围一致，**未跟踪的新文件逐个打开读**（裸 diff 看不到它们）；
2. `git diff HEAD`——覆盖已跟踪文件的全部改动（含已暂存部分）；
3. 任务书 + 上游 RFC / PRD。

**评审动作**：
1. **独立复跑**验证命令，不采信实现报告里的"已通过"；
2. 逐条核对验收场景；
3. 核对禁区与范围外文件未被触碰，且任务书契约部分（范围 / 禁区 / 验收）未被改动；
4. **风险触发检查**：安全面、失败模式与错误处理、兼容性、新增依赖、可观测性——任一被触发就展开审查；
5. 结论（含 base_sha）写入任务书评审记录：通过 → status: reviewed 并**立即做实现提交**（评审与提交之间不得有任何其他写入），随后按一图流 ⑧ 做收尾提交；不通过 → 问题清单回实现者。

返工上限 2 轮：第 3 次仍不过，说明任务书或 RFC 本身有问题，停下来找人。major 级须人工复核代码后方可提交。

## 6. 强制机制与触发器清单

**三层强制（现状如实）**：
1. **约定层**（已生效）：AGENTS.md + 本文件。
2. **钩子层**（部分生效，`scripts/hooks/` + `core.hooksPath`）：commit-msg 强制身份前缀；任务号引用当前为警告，**自首个 normal-lite 及以上任务完成起升级为拦截**。pre-commit（跑 `check`、校验上游文档状态）**依赖技术栈，尚未存在**。
3. **CI 层：尚未存在**（依赖远程仓库）。在此之前，"强制"仅覆盖提交信息格式，其余靠约定层。

**触发器清单（到点必须建，未到点不许建）**：
- 首个业务代码提交前：远程仓库 + 受保护 main + 最小 CI（跑唯一 `check` 命令）+ secret 扫描 + 依赖锁定
- 首次部署前：一页 release checklist（候选 SHA / 制品、环境与配置、迁移、上线验证、回滚触发器与负责人）
- 首次生产 / 真实用户可访问的部署前：一页 incident runbook（严重度分级、止血授权——人可先回滚 / 关功能、事后限时补文档、高等级事故强制复盘）
- 首次处理真实用户数据前：数据分类、保留策略、迁移备份与恢复清单
- 出现并行任务需求时：per-task git worktree + 集成队列
- 巡检为触发式：每次 release 前 / 重大迁移后 / 每季度，做一次文档-代码一致性巡检并出报告

## 7. 与飞书的接口（单一评审面）

每份文档在任一时刻只有**一个**评审面：
- 起草与初次评审期：飞书（PM 自由协作、评论）；
- 人批准并入库那一刻起：git 为唯一评审面与权威源（frontmatter 记 `feishu` 证据链接与 `approvers`）；
- 后续修订评审在 git 侧进行；需要 PM 参与时导出**只读**镜像收集意见，由编排者整理成升版提案，不做双向正文同步。
